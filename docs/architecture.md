# voice-notifier Phase 1 設計レビュー案

## 対象と環境

既存の音声生成処理が保存した MP3 を検知し、前面表示中の iPhone で順次再生する。CDK と既存 S3 のリージョンは `ap-northeast-1`。バケットはデプロイ先と同じアカウントにあり、バージョニングは無効。日時などを含むキーを使い、上書きは行われない。KMS はデフォルトのキーとの回答をもとに、実際の暗号化方式とキーをデプロイ前に確認する。

CDK は `AUDIO_BUCKET_NAME` と `AUDIO_KEY_PREFIX` を環境変数から読み、必須設定として検証する。CDK はバケットを名前で参照し、Lambda には必要な設定を環境変数で渡す。MP3 は初期の対象形式とし、対象プレフィックスと拡張子を取り込み Lambda でも確認する。

## 構成と S3 連携

```text
既存 S3 → S3 ObjectCreated → Python 取り込み Lambda → DynamoDB
                                                        ↓ Streams
iOS SwiftUI ← API Gateway WebSocket ← 配信 Lambda ← 音声レコード追加
iOS SwiftUI → API Gateway HTTP API → API Lambda → DynamoDB / S3 URL 署名
iOS SwiftUI → 署名付き URL で S3 から直接ダウンロード
```

S3 の直接イベントを受ける方式を第一候補とする。既存の通知設定を確認し、再利用できる経路があるかを調べる。新規通知を追加する場合は、バケット所有側での変更を別途レビューし、既存設定の全項目を保持する。対象プレフィックスと `.mp3` のフィルターが既存ルールと重複する場合は、通知経路を決め直す。S3 の通知設定 API は設定全体を置換するため、本アプリの CDK は通知設定の更新権限や自動更新処理を持たない。CDK は取り込み Lambda と、対象バケット・アカウントに限定した呼び出し許可を作成する。

直接イベントの各レコードから S3 キーを URL デコードし、バケット、プレフィックス、イベント種別、拡張子を検証する。上書きなしの前提でバケット名とキーから決定的な音声 ID を作る。条件付き書き込みで重複を防ぎ、音声メタデータと取り込み順を保存する。取り込み順の採番とレコード追加は同一トランザクションで行う。遅れて到着したイベントは取り込み順の末尾に入る。取り込み Lambda の非同期実行には失敗時送信先を構成する。

DynamoDB Streams を起点に配信 Lambda が通知する。クライアントは通知を受けて HTTP 一覧を同期し、再接続と前面表示中の定期同期でも未処理項目を回収する。配信処理は将来の通知方式を追加できるよう独立させる。

## API と認証

| 経路 | 用途 |
| --- | --- |
| `POST /v1/devices` | 管理者が発行した短命の一回限りの登録コードを端末 ID とトークンに交換 |
| `GET /v1/audio?cursor=…` | 未処理音声を取り込み順で返す。各項目に `audioId` と `createdAt`、必要に応じて `nextCursor` |
| `POST /v1/audio/{audioId}/download` | 認可済みの音声に対して `url` と `expiresAt` を返す |
| `PUT /v1/audio/{audioId}/played` | 端末単位で再生完了を記録。同じ完了通知は再送可能 |
| WebSocket `$connect` | Authorization ヘッダーの端末トークンを Lambda オーソライザーで検証 |
| WebSocket サーバー通知 | `{"type":"audio.available","version":1,"audioId":"…"}` |
| WebSocket ハートビート | `{"action":"ping"}` → `{"type":"pong","version":1}` |

登録コードは条件付き更新で一回だけ消費する。端末トークンは高エントロピーの乱数とし、端末側は Keychain、サーバー側はハッシュと失効状態を保持する。失効時は WebSocket 接続も閉じる。登録以外の HTTP API は端末認証を必須とする。カーソルはページ送りに使い、処理済みの判定には端末ごとの連続した再生完了位置を使う。完了通知が次の取り込み順を飛ばす場合は HTTP 409 を返す。

S3 は非公開のまま維持する。署名 Lambda の S3 読み取りは対象プレフィックスに限定し、署名付き URL は初期値 60 秒とする。SSE-KMS が確認された場合は対象キーの復号権限を確認する。AWS 認証情報はアプリへ組み込まず、登録コード、トークン、署名付き URL はログに出さない。

## iOS

SwiftUI の `scenePhase` が `.active` の間、`URLSessionWebSocketTask` で接続を維持する。4 分間隔のハートビート、ジッター付き指数バックオフ、前面復帰と再接続時の同期を実装する。API Gateway のアイドル上限は 10 分、接続上限は 2 時間。

ローカル再生キューは音声 ID で重複を排除する。各音声は再生直前に URL を取得して一時ファイルへダウンロードし、AVFoundation で一件ずつ再生する。再生完了を端末へ保存してから API に送り、通信失敗時は再送する。再生エラーは未完了として再試行できるようにする。

## ディレクトリと実装段階

- `infra/` に CDK TypeScript とテンプレート検証を置く。
- `backend/` に Python Lambda と単体テストを置く。
- `ios/` に SwiftUI の Xcode プロジェクトとテストを置く。

設計レビュー後に CDK、取り込み、認証、HTTP API を実装し、続いて WebSocket と iOS を接続する。ローカルでは重複と順序逆転、対象外キー、登録コードの競合、失効、完了通知の再送を検証する。`cdk synth` では既存 S3 の作成・変更が含まれないことを確認する。承認された環境でのデプロイ後、実機で連続投入、前面復帰、ネットワーク切断、URL 失効、再生中断を検証する。

1 端末、前面接続 2 時間/日、月 300 件、平均 1 MB を仮定すると、月 3,600 接続分と約 0.3 GB の配信になる。追加費用は月 1 USD 未満を初期目安とする。既存の生成・保存費用と税は除き、KMS とログは実際の利用状況に応じて見直す。

## レビューで確認する事項

- 管理者登録の 1 端末と取り込み順での再生はレビュー承認済み。
- バケット名とプレフィックスは環境変数で設定する。デプロイ前に既存通知の対象・宛先、暗号化方式とキーを確認する。
- 既存通知を再利用できない場合、バケット所有側で既存通知を保持したまま直接通知を追加できるか確認する。
- ロック中の再生と APNs / Push to Talk は Phase 2 の検証対象。複数ユーザー・端末と配布は Phase 3。
